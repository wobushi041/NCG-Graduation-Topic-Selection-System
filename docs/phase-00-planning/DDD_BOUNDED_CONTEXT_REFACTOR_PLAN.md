# 三个限界上下文重构计划

## 1. 状态与目标

- 状态：边界讨论记录，待实施；不是已经完成的架构说明，也不是可直接执行的完整实施方案。
- 记录日期：2026-10-11。
- 范围：在现有单体后端内，逐步建立身份与账号、教学组织、毕业选题三个限界上下文。
- 本次交付：记录已确认的职责、协作原则、待重构项和后续验证要求，不修改代码、接口或数据库。

目标是明确业务语言、规则和状态的所有权，不是仅移动包或增加一层 Service。三个上下文是当前业务下的初始划分，不意味着三个微服务、三个数据库或三个永久不变的领域。

## 2. 已确认的上下文边界

| 上下文 | 核心问题 | 拥有的职责 | 不应拥有的职责 |
|---|---|---|---|
| 身份与账号 | 谁在访问系统，以什么身份访问？ | 账号标识、账号状态、凭证、密码、邮箱绑定、验证码、登录会话、访问角色及角色切换 | 学生选题资格、教师出题额度、选题负责人审核范围 |
| 教学组织 | 学生或教师在教学组织中属于哪里？ | 学院、专业、学院与专业的隶属关系、学生所属专业、教师所属学院、组织关系有效性 | 选题组专业范围、题目状态、选题模式和选题结果 |
| 毕业选题 | 谁能在什么条件下提供、审核和选择题目？ | 选题组及专业适用范围、负责人审核范围、教师组内出题额度、题目生命周期、预选、确认、教师分配、退选、名额和选题策略 | 账号凭证、登录会话、学院和专业本身的维护 |

### 2.1 选题组归属决定

本次讨论已确认以下划分：

- 学院、专业是什么，以及两者的隶属关系：教学组织负责。
- 学生属于哪个专业、教师属于哪个学院：教学组织负责。
- 选题组允许哪些专业参与、题目属于哪个选题组：毕业选题负责。
- 教师组内出题额度、负责人审核哪些题目：毕业选题负责。

选题组的主要职责是限制哪些专业的学生能够选择哪些题目，因此属于选题资格配置，不属于学校组织层级。关联专业或学院，不代表其领域所有权属于教学组织。

现有选题组计划已经记录“一个专业只归属一个选题组，一个选题组可以包含多个专业”。本计划以此作为现有基线，不自行扩展为多对多关系；正式实施前复核该规则是否仍适用。

### 2.2 毕业选题内部模块

毕业选题上下文内部可按职责组织为：

| 内部模块 | 职责 |
|---|---|
| 选题组织与规则 | 选题组、专业适用范围、负责人范围、教师出题额度、跨学院策略、选题模式、退选锁定规则 |
| 课题管理 | 题目提交、审核、修改、发布、撤销发布和删除 |
| 选题分配 | 预选、取消预选、学生确认、教师分配、退选及名额维护 |

这些是同一上下文中的内部模块，不预先认定为三个独立上下文，也不合并成一个巨大聚合。具体聚合、领域服务和仓储边界留待用例与一致性分析后确定。

当前确认选题会同时修改选题记录和题目余量，题目撤销发布、删除也受到选题关系约束，因此暂不拆分课题管理与选题分配的上下文。

## 3. 当前实现与目标之间的差距

| 当前实现依据 | 待重构方向 |
|---|---|
| `AuthenticationService`、`PasswordService`、`VerificationCodeService` 已分别承接认证、密码和验证码能力 | 归入身份与账号边界，进一步区分用例编排、业务规则和基础设施适配 |
| `User` 同时保存凭证、角色、学院、专业和负责选题组等信息 | 建立账号、组织成员、选题参与者等不同语义模型或视图；不要求立即拆表 |
| `OrganizationApplicationService` 同时管理学院、专业、选题组和教师组额度 | 保留教学组织职责，将选题组及额度相关规则逐步归入毕业选题 |
| `Major.topicGroupId`、`User.topicGroupId` 保存选题相关关系 | 先明确选题关系的修改所有权，再评估存储调整；字段所在表不等于所属上下文 |
| `TopicApplicationService`、`TopicSelectionApplicationService` 同时承担编排、规则判断和持久化调用 | 逐用例提取领域规则，用应用服务保留事务、加载、调用和保存的编排 |
| `UserApplicationService` 删除学生时清理选题并恢复题目计数 | 由跨上下文流程协调毕业选题的公开清理能力，避免账号模块重复维护名额规则 |
| `SelectionPolicyService` 管理选题开关、跨学院配置，同时提供系统信息 | 选题策略归毕业选题；技术系统信息不因此成为选题领域模型 |
| 多个流程直接传递持久化实体并调用其他业务的基础 Service | 引入最小公开契约及必要事实对象，减少跨上下文对内部 Entity、Mapper 的依赖 |

当前已有应用服务拆分，并不等于已经完成严格 DDD。保留现有业务行为，不能把目标结构描述为当前事实。

## 4. 四层职责与跨上下文协作

每个上下文内部按 API → Application Service → 领域 → 持久化适配组织职责：

| 层 | 职责 |
|---|---|
| API | HTTP 路由、请求绑定、基础字段校验、调用用例、响应适配 |
| Application Service | 当前操作者获取、用例编排、事务边界、加载和保存、跨上下文能力协调 |
| 领域 | 本上下文的资格判断、状态转换、不变量及其他业务规则 |
| DAO／基础设施适配 | SQL、锁、持久化映射，以及 Redis、会话、邮件等外部能力适配 |

四层是职责和依赖边界，不要求所有调用都机械地经过四个对象。应用服务可以通过仓储接口加载与保存；纯查询可以通过查询服务读取投影，不必制造无行为的领域模型。

### 4.1 协作原则

1. 应用服务通常归属于用例的主导上下文；确有跨上下文流程时，可以设置专门的协调应用服务。
2. 可以有多个 Application Service，按相关用例组织，不设置全系统万能编排服务，也不要求每个接口对应一个类。
3. 同一上下文内部允许领域对象与领域服务协作；跨上下文依赖公开契约，不直接访问对方 Mapper 或修改对方内部状态。
4. 教学组织提供组织事实，毕业选题解释并执行选题资格规则，避免双方各维护一套相同规则。
5. 账号访问角色归身份与账号；具体负责哪个选题组、能审核哪些题目归毕业选题。角色切换中需要的组织事实通过教学组织公开能力获得。
6. 初期保持单体内 Java 调用，不引入 HTTP、消息队列或微服务作为划分上下文的前提。
7. 同一业务规则只能有一个权威实现；不同上下文允许使用不同模型表达同一个人或同一标识。

### 4.2 代表用例

| 用例 | 主导／协调应用层 | 上下文协作 |
|---|---|---|
| 学生确认选题 | 毕业选题应用服务 | 身份与账号提供操作者身份；教学组织提供学生专业等事实；毕业选题判断资格、状态和名额并保存结果 |
| 教师发布题目 | 毕业选题应用服务 | 获取教师身份和组织事实；毕业选题检查组内额度、审核与发布条件 |
| 创建学生账号 | 账号开户应用流程 | 教学组织校验学院、专业及隶属关系；身份与账号创建账号；教学组织建立成员关系 |
| 删除学生账号 | 账号注销协调流程 | 毕业选题清理选题关系并释放名额；教学组织处理成员关系；身份与账号删除账号并使会话失效 |

“学生确认选题”的目标交互为：

```text
API
  → 毕业选题应用服务
      → 身份与账号公开能力：获取操作者身份
      → 教学组织公开能力：获取学生专业等组织事实
      → 毕业选题仓储：加载选题组、题目、选题记录与策略
      → 毕业选题领域：判断资格并执行确认
      → 毕业选题仓储：保存选题结果和题目名额
```

这是目标职责描述，不是当前方法调用栈，也不预先确定每一步的加载与加锁顺序。

## 5. 渐进重构顺序

### 阶段一：用例与规则基线

- [ ] 梳理三个上下文的写入入口、查询入口、规则和数据所有权。
- [ ] 明确专业与组、负责人和组、教师和组的数量关系。
- [ ] 分别记录预选、学生确认、教师分配、退选和删除账号的现有行为，不能默认它们共用全部规则。
- [ ] 明确出题额度、题目容量、剩余名额和 `selectAmount` 的业务含义。
- [ ] 固定 API 契约及核心回归场景，区分架构调整与业务规则变更。

阶段产物：上下文职责清单、规则台账、待确认决策和测试基线。

### 阶段二：建立公开契约与职责所有权

- [ ] 定义必要的账号身份、教学组织事实和毕业选题公开能力。
- [ ] 区分内部持久化实体与跨上下文传输模型，不一次性改写全部模型。
- [ ] 将选题组、专业适用范围、负责人范围和教师额度的修改入口收口到毕业选题。
- [ ] 在保留原 API 的前提下，逐步减少跨上下文直接依赖 Mapper 和内部 Service。

阶段产物：可验证的模块依赖边界；包名、接口名称及是否拆 Maven 模块在实施方案中确定。

### 阶段三：以学生确认选题做垂直重构

- [ ] 将资格、状态、唯一最终选题和名额约束整理为毕业选题领域规则。
- [ ] 应用服务保留事务、必要事实获取、加载、领域调用和保存。
- [ ] 持久化适配保留悲观锁、SQL 和模型映射，明确跨模型一致性方案。
- [ ] 验证成功、资格不符、题目未发布、时间限制、重复确认、满额、并发和回滚场景。

先用一个完整用例验证结构，再推广到预选、教师分配、退选和课题生命周期，不一次性搬迁全部代码。

### 阶段四：扩展用例并治理跨上下文流程

- [ ] 将其他选题与课题用例逐步迁移到同一职责模型。
- [ ] 重构开户、账号删除及组织删除等跨上下文流程，明确每个步骤的状态所有者。
- [ ] 通过毕业选题公开能力复用选题清理和名额恢复规则。
- [ ] 按业务归属安置查询、报表、导入导出，不增加独立 reporting 上下文。
- [ ] 明确邮件、会话失效等副作用的提交后执行、失败处理和重试要求。

## 6. 一致性与兼容性约束

- 保持现有 API 路径、请求字段、响应字段和业务状态码；接口归属变化不要求同步改路由。
- 不因上下文划分自行改变选题条件、角色切换规则或专业与选题组的数量关系。
- 不在本计划中安排强制拆表、拆数据库、微服务迁移或替换鉴权框架。
- 单体共用数据库时，确需原子完成的跨上下文用例可以由协调应用服务控制本地事务；不能把所有业务扩大成一个长期大事务。
- 当前选题写流程采用学生 → 题目 → 选题记录的加锁路径；多题目清理需复核固定锁顺序。边界迁移不得无意破坏防超选和回滚能力。
- 当前学生锁使用 `User` 数据行。未来账号模型与选题参与者模型分离时，必须设计等价的并发互斥机制，不能删除该锁后仍宣称保证唯一最终选题。
- 不要求领域层依赖 Servlet、`BaseResponse`、MyBatis 查询条件、Redis 键或 Sa-Token 实现；这些通过边界适配。
- 边界稳定不等于规则不变：用例变化调整应用编排，业务规则变化调整领域模型，语义和所有权变化再评估上下文。

## 7. 实施前待确认事项

| 问题 | 当前处理 |
|---|---|
| 一个专业是否仍只能参加一个选题组？ | 现有计划与字段按一个专业一个组建模；没有获得改成多对多的授权 |
| 学生确认与教师分配的时间、跨学院条件差异是否有意？ | 分别保留现状，补齐规则台账后确认，不能在提取领域规则时自动统一 |
| `selectAmount` 统计预选人数还是有效选题关联数？ | 当前不同路径存在预选新增、直接最终分配新增和清理减计数，须核定统一术语 |
| 组内教师出题额度与题目学生容量如何命名？ | 是两种不同约束，不能抽象成同一个泛化额度规则 |
| 组织归属或组专业范围修改后，已有选题是否保留资格？ | 需要业务决定；事实读取、快照或版本策略在实施阶段明确 |
| 账号删除、组织删除与选题清理的原子范围是什么？ | 逐用例明确事务、阻止条件和副作用，不预设所有步骤最终一致 |
| 选题组关系是否需要从现有表迁出？ | 优先建立职责边界，再依据完整模型和一致性要求决定物理结构 |

## 8. 后续验收要求

- 三个上下文的核心规则和修改入口具有明确所有权，选题组及专业适用范围属于毕业选题。
- 不同上下文通过公开能力协作，领域核心不直接使用其他上下文的 Mapper 或内部持久化模型。
- 确认、分配、退选、删除账号等流程不重复实现名额维护规则。
- 核心选题用例具备领域规则测试、应用编排测试及持久化并发／回滚测试。
- 原有接口契约、鉴权与横切顺序保持兼容。
- 根据变更范围运行后端相关测试；接口或持久化改动优先执行根目录 `.\mvnw.cmd verify`（运行集成测试需要可用的容器环境）。
- 增加可执行的模块依赖约束测试，不能仅靠目录名称判断边界是否成立。

本次仅新增计划文档，以上是未来实施验收要求，不是本次已完成项。
